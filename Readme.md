
# Практическая работа № 7. Межпроцессное взаимодействие (IPC) — Уровень B

## 🎯 Цель работы

Освоить практические навыки организации межпроцессного взаимодействия (IPC) в ОС Linux с использованием различных механизмов: именованных каналов (FIFO), Unix Domain Sockets и разделяемой памяти (`multiprocessing.shared_memory`), а также провести их сравнительный анализ по скорости и сложности использования.

---

## 🛠 Описание реализованных задач

### 1. Клиент–серверное приложение на именованных каналах (FIFO)

* **Реализация:** Сервер создает два именованных канала: `/tmp/req_fifo` (для приема запросов) и `/tmp/resp_fifo` (для отправки ответов).
* **Принцип работы:** Клиент вычисляет арифметические выражения, передавая строку в `req_fifo`, сервер обрабатывает запрос (выполняет безопасный парсинг/вычисление) и возвращает результат через `resp_fifo`.
* **Особенности:** В коде учтено требование корректного порядка открытия каналов (`os.O_RDONLY` / `os.O_WRONLY`), чтобы исключить взаимные блокировки (deadlock).

### 2. Сервис на Unix Domain Sockets (`socket.AF_UNIX`)

* **Реализация:** Сервер создает потоковый Unix-сокет по адресу `/tmp/unix_socket` и обрабатывает подключения нескольких клиентов одновременно (создавая по отдельному потоку/процессу на каждого клиента).
* **Принцип работы:** В отличие от FIFO, Unix-сокет обеспечивает полнодуплексную двухстороннюю связь в рамках одного дескриптора. Сервер считывает выражение, вычисляет значение и отправляет ответ в тот же сокет.

### 3. Сравнение производительности: `Shared Memory` vs `Pipe`

* **Объем данных:** Передача массива из **10 000 000** целых 32-битных чисел (порядок ~40 МБ данных в бинарном виде).
* **Механика Pipe:** Данные сериализуются и копируются через буфер ядра из пространства пользователя одного процесса в другой.
* **Механика Shared Memory:** Используется модуль `multiprocessing.shared_memory`. Процесс-приемник отображает ту же область физической памяти в свое адресное пространство и читает данные напрямую через `array.frombytes()` без пересылки и копирования через ядро.

## 📊 Сравнительная таблица механизмов IPC

| Механизм IPC | Нужна ли синхронизация со стороны программиста? | Объём данных | Время передачи / Относительная скорость |
| --- | --- | --- | --- |
| **Pipe (Анонимный канал)** | **Нет** (управляется и блокируется ядром ОС) | Малый / Средний | Низкая / Средняя (копирование буфера через ядро) |
| **FIFO (Именованный канал)** | **Нет** (блокировки при открытии/чтении файловой системой) | Малый / Средний | Средняя |
| **Unix Domain Socket** | **Нет** (управляется сетевым стеком ядра для IPC) | Средний / Большой | Высокая (оптимизированный стек IPC) |
| **Shared Memory (Разделяемая память)** | **Да** (обязательно нужны мьютексы/семафоры) | **Любой (очень большой)** | **Максимальная** (передача по указателю, 0 копирований) |

## 🧹 Инструкция по очистке ресурсов

Для предотвращения «утечек» ресурсов после завершения работы программ автоматически выполняется удаление созданных временных файлов:

* Удаление FIFO: `os.unlink('/tmp/req_fifo')` и `os.unlink('/tmp/resp_fifo')`
* Удаление Unix-сокета: `os.unlink('/tmp/unix_socket')`
* Освобождение сегментов памяти: `shm.close()` и `shm.unlink()`

Проверить отсутствие «зависших» сегментов разделяемой памяти в Linux можно командой:

```bash
ls -l /dev/shm

```

## ❓ Ответы на контрольные вопросы

### 1. Почему разделяемая память — самый быстрый и самый опасный механизм IPC?

* **Почему самый быстрый:** Это единственная технология IPC, которая не требует системных вызовов чтения/записи (`read`/`write`) и копирования данных между пространством пользователя (User Space) и пространством ядра (Kernel Space). Оба процесса читают и пишут в одну и ту же физическую планку ОЗУ.
* **Почему самый опасный:** Операционная система никак не арбитрирует одновременный доступ процессов к разделяемой памяти. Если два процесса попытаются одновременно записать данные в одну ячейку памяти без использования внешних средств синхронизации (мьютексы, семафоры), произойдет **состояние гонки (race condition)** и повреждение данных.

### 2. Что произойдёт при записи в pipe, у которого закрыты все читающие концы?

При попытке записать данные в канал (`pipe`), из которого никто не читает (все читающие дескрипторы закрыты):

1. Операционная система отправляет процессу-писателю сигнал **`SIGPIPE`**.
2. По умолчанию обработчик сигнала `SIGPIPE` **аварийно завершает** процесс.
3. Если процесс перехватывает или игнорирует `SIGPIPE`, системный вызов записи вернет ошибку **`EPIPE`** (*Broken pipe*).
